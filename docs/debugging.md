# Debugging

## A debugger (`zfls dap`)

`zfls dap` is a debug adapter (the Debug Adapter Protocol on standard input and output) that shows a Fortran program as Fortran, for any editor with a client of the protocol (VS Code through the extension's `fortran` debug type, Neovim's nvim-dap, Emacs's dape, Helix). It debugs with one of three debuggers, chosen by the `launch` or `attach` configuration, else by the program's debug information, with the rule `zfls/buildCommand` answers with: Windows's Debugger Engine for a program whose debug information is Microsoft's only (a PE whose debug directory names a PDB, without DWARF sections), even where the configuration names gdb or lldb-dap, which cannot read it; else gdb on Linux and Windows and lldb-dap on macOS. The choice by the program is said in the Debug Console (an `output` event); `"dbgeng": false` keeps a configuration from the engine.

- gdb, for the programs of gfortran, LLVM Flang, LFortran and the others with DWARF debug information: gdb 14 or later, built with Python (`gdb -i=dap`), the configuration's `gdb`, else `--gdb PATH`, else the `PATH`'s. zfls passes gdb's protocol through and reshapes its variables: arrays by their subscripts and bounds (`(2,-1)`), large ones in sections (`(1:100)`), previews of arrays and derived types (`[1.0, 2.0, …]`, `[2×3]`, `point(x=9.0, id=7)`), "not allocated" and "not associated", pointers as their targets, a polymorphic object with its dynamic type's components, gfortran's hidden CHARACTER lengths and LFortran's temporaries left out, CHARACTER of kind 4 and arrays of it as Fortran strings (`4_'hëllo'`, an element by its subscripts `w(2,1)`), and a Fortran expression for each (`a(2)`, `p%x`, `grid::cells`) for watches and setting values. `console` (`integratedTerminal`, `externalTerminal`) runs the program in a terminal for its input; `setupCommands` are gdb commands run first; `stopAtEntry` stops at the main program; an `attach` takes a `processId` or a gdbserver's `target`. On Linux AArch64 with SVE, gdbserver 15.1 to 16.2 (Ubuntu 24.04's is 15.1) fails an assertion of its own (`raw_compare: Assertion 'offset < regbuf.size ()' failed`) as the program first goes on, which then runs to its end past its breakpoints, with gdb's own commands too; gdb 16.3 fixed it: use gdbserver 16.3 or later there.
- lldb-dap, LLVM's debug adapter (`"lldb": true` or `"lldb": PATH`, or `--lldb [PATH]`; the default on macOS, where gdb does not run on Apple Silicon and must be code-signed with a certificate of one's own on Intel, and `"gdb": PATH` still chooses gdb): the configured one, else `xcrun --find lldb-dap` on macOS (Xcode's command line tools have it, signed: `xcode-select --install`), else the `PATH`'s `lldb-dap`, else its `lldb-vscode`. zfls passes its protocol through: breakpoints of lines and functions, stepping, the stack, `console`, `stopAtEntry`, an `attach` to a `processId`, and `setupCommands` as lldb commands. lldb reads no Fortran ("no plugin for the language fortran95"): for the programs of gfortran and LLVM Flang its Variables view is empty (its globals show without values), expressions are not evaluated, and there is no module variables scope. LFortran's debug information says its language is C, so lldb shows their integer and real scalars (without LFortran's temporaries). On Windows, lldb-dap of LLVM 23.1.6 or later (LLVM's Windows installer, `LLVM-23.1.6-win64.msi`, has it, not its `clang+llvm` archive; its `liblldb.dll` needs a Python's `python3.dll` on the `PATH`), with MinGW's gfortran programs, attaching too; gdb stays the default there. An older one (LLVM 21's, the Swift toolchain's) stops the program but tells the stop only when it is asked something else, so zfls refuses it and names gdb and the Debugger Engine. LLVM 23's lldb on Windows can tell a stop at the runtime's errors and ERROR STOP twice, and zfls continues the second ([#947](https://github.com/cesiumlang/zfls/issues/947)). With a gdb code-signed for debugging on an Intel Mac (gdb 17.2 on macOS 15), breakpoints, stepping, the variables, COMMON blocks, conditions and completions work, but not the stops at ERROR STOP and at gfortran's runtime errors (gdb does not set breakpoints in libgfortran's dynamic library there), attaching (gdb finds no threads of the process) or data breakpoints, and gfortran's hidden CHARACTER lengths show among the variables: lldb-dap, the default, has the stops and the attach. The signed `zfls` of a release (hardened runtime, no entitlements) debugs with lldb-dap and with gdb as an unsigned one does: the debuggers are processes of their own, with their own signatures. A debugger that does not answer `initialize`, `launch`, `attach` or `disconnect` within two minutes fails that request. Over ssh, macOS lets a debugger start a program only with Developer Mode on (`sudo DevToolsSecurity -enable`).
- Windows's own Debugger Engine (`"dbgeng": true`, or `--dbgeng`, or chosen by the program; `dbgeng.dll` of System32, which every Windows 10 and later has), for the programs whose debug information is Microsoft's: those of ifx and ifort on Windows, and LLVM Flang's built with `-g` (with `-gdwarf-4` they are gdb's too). It launches the program (in a console window of its own) or attaches to it, stops at breakpoints of source lines, steps by lines, and shows the variables as Fortran: dbghelp says where each is, and zfls's declarations its type, kind and rank; arrays are read through Intel's and LLVM Flang's descriptors. For LLVM Flang's programs it has breakpoints, the stack, stepping, the variables (a polymorphic object with its dynamic type) and the stops at runtime errors; gdb reads the variables from a build with `-gdwarf-4 -Wl,-debug:dwarf` too.

With gdb and the engine, the module variables that the frame's line sees are a scope of their own (zfls indexes the program's sources: `sourceRoot` of the configuration, else `cwd`), and the Debug Console completes the names of Fortran: after `%` the components of the designator before it (`origin%`, `p t%po` with gdb, whose console takes its commands), else the frame's variables and those module variables (gdb's own completion of its commands stays). With the engine, breakpoints take conditions, hit conditions and log messages as gdb's do, in Fortran (`k == 1`, `k .ne. 0 .and. p%x > 0`, `k is {k}`), which zfls evaluates at each hit, and Set Value sets a scalar, an element or a component to a Fortran expression's value (INTEGER, REAL, LOGICAL and CHARACTER; not arrays, derived types or COMPLEX). The engine also takes function breakpoints by a procedure's Fortran name (`work`, `grid::work`, the main program by its name or `main`, found at the symbol Intel or LLVM Flang gives it; else a symbol as given), with conditions, hit conditions and log messages; data breakpoints on a scalar, an array's element or a small component (the processor's breakpoints, of 1, 2, 4 or 8 bytes at an address of their size's alignment; a whole array or a derived type has none, and `dataBreakpointInfo` says why); and the memory, disassembly, modules and loaded sources views (`readMemory` from a variable's or a frame's address, `disassemble`, `modules`, `loadedSources`). An `attach` with `"dbgeng": true` attaches the engine to a `processId` (a number, or the text `${command:pickProcess}` gives) without gdb. A module's COMMON variables, of which gfortran's DWARF has only the block, are read at their places in the block (zfls's declarations give their types and the offsets), of every intrinsic type, CHARACTER of a constant length, a SEQUENCE type the program has elsewhere, and any constant shape, also in expressions (`cm(2,3) + cx`). With all three, the exception filter **Fortran runtime errors** stops the program where the Fortran runtime reports an error (an array bound exceeded under `-fcheck=bounds`, a failed allocation, an I/O error without `iostat=`, `err=` or `end=`) or at ERROR STOP, LLVM Flang's and LFortran's runtimes' too. With gdb, data breakpoints watch a scalar, an array's element or a small component (gdb's hardware watchpoints, at its address); a whole array or more than 8 bytes has none, and `dataBreakpointInfo` says why. gdb's filters of C++ exceptions are shown only for a program that links a C++ runtime (libstdc++, libc++, MSVC's `msvcp140.dll`, by its file at the launch or attach, in a `capabilities` event), or for any with `"cppExceptionFilters": true` in the configuration.

A program of coarrays linked with gfortran's `-fcoarray=lib -lcaf_shmem` (GCC 16) runs each image as a process of its own, which neither gdb nor lldb-dap follows (gdb on Windows debugs no child process): its breakpoints, runtime errors and ERROR STOP in the images do not stop, and `zfls dap` says so in the Debug Console at the launch. Build it with `-lcaf_single` to debug one image in the program's own process.

An MPI program is debugged a rank to a session, on Linux: a `launch` with `"mpi": { "ranks": 4 }` runs the launcher (`launcher`, by default `mpiexec`, with `launcherArgs` before its `-n`) in the editor's terminal with each rank under a gdbserver of its own (`gdbserver`, on port `port`, by default 20000, plus the rank), then asks the editor to start a session per rank, each attaching gdb to its rank's gdbserver with the launch's `program`, `cwd`, `sourceRoot` and `gdb`. The breakpoints, stepping and variables are the ranks' sessions'; ending the launch's session hangs up the terminal, and with it the ranks. It needs a client that runs commands in a terminal and starts sessions (`runInTerminal`, `startDebugging`), as VS Code does. Open MPI, MPICH, Intel MPI and Slurm's ranks are told by their variables; CI tests it with Open MPI (Ubuntu 24.04's MPICH runs each rank as a job of its own, debugger or not).

On Windows, MSYS2's gdb reads no symbols of `libgfortran-5.dll`: a breakpoint on one of its functions by name lands in the program's import thunk only, and so misses the errors the runtime raises inside the DLL (an I/O error, `RANDOM_SEED`, `MATMUL`'s shapes). For a program linked with the DLL, zfls dap reads the DLL's export table when gdb loads it (gdb's Python) and sets the filter's breakpoints at those functions' addresses in the DLL instead, so they stop there too. Debug Fortran File builds gfortran's programs with `-static-libgfortran -static-libquadmath` on Windows all the same. `--text JSON` translates the words it shows (the VS Code extension passes them in VS Code's language).

With nvim-dap, for instance:

```lua
local dap = require("dap")
dap.adapters.zfls = { type = "executable", command = "zfls", args = { "dap" } }
dap.configurations.fortran = {
  {
    type = "zfls",
    request = "launch",
    name = "Debug",
    program = function() return vim.fn.input("Program: ", vim.fn.getcwd() .. "/", "file") end,
    cwd = "${workspaceFolder}",
    sourceRoot = "${workspaceFolder}",
  },
}
```

With dape (Emacs):

```elisp
(add-to-list 'dape-configs
             '(zfls modes (f90-mode fortran-mode) command "zfls" command-args ("dap")
                    :request "launch" :program "a.out" :cwd "." :sourceRoot "."))
```

With Helix, in `languages.toml`:

```toml
[[language]]
name = "fortran"
debugger = { name = "zfls", transport = "stdio", command = "zfls", args = ["dap"], templates = [
  { name = "launch", request = "launch", completion = [{ name = "program", completion = "filename" }], args = { program = "{0}" } },
] }
```

## Module variables, for a debugger

`zfls/moduleVariables` (a position) gives the module variables that the line sees: those of the module or submodule around it (private ones too, and a submodule's ancestors'), then those its USE statements, and its hosts', make visible, each with the module that declares it, its name there, its name at the line (a USE may rename it) and its type; named constants are left out. `zfls dap` shows them, with their values, as a scope of the Variables view; with the C debuggers, whose variables view leaves them out, the VS Code extension shows them in a view of their own.

## Inline values, while debugging

`textDocument/inlineValue` gives, while a debugger is stopped, the places from the first line of the procedure (or program) that holds the stop down to the stop where its variables are used: its locals and dummy arguments, its host procedures', and the module variables the line sees, under the names `zfls dap` lists them by. The editor then shows each one's value at the end of its line (VS Code: `debug.inlineValues`). Named constants, components, procedures, types, strings and comments are left out.
